# M16.5 — Language Surface Normalization Gate

Goal: turn the measured grammar-construction hotspots into an evidence-backed normalization decision before broad M17–M20 language-surface implementation, without changing AIDL syntax or semantics in this milestone itself.

Dependencies: M7 remains the sole compatibility-classification authority; M10 provides conformance/evidence discipline; M16 provides the model-independent construction/change evaluation approach; `docs/06-grammar.md`, `docs/grammar-complexity-review.md`, and `tools/grammar_complexity_metrics.py` provide the current deterministic syntax baseline.

This milestone is a planning and decision gate. It does not define replacement syntax, change parser behavior, promote support claims, or authorize a breaking change. Any later syntax change requires its own versioned language decision, implementation, compatibility evidence, migration plan, fixtures, and conformance updates.

## Why this gate exists

The current deterministic grammar inventory records 16 normative EBNF sections, 182 productions, 456 top-level production alternatives, 318 non-lexical syntax terminals including 298 word-shaped contextual terminals, 111 logical-newline leaf alternatives, 62 block alternatives, 40 colon alternatives, 19 list alternatives, and 295 coarse starter-plus-shape signatures. The construction review normalizes those rules into 16 recurring families and classifies the language as moderately in need of simplification rather than structurally unmanageable.

The highest-risk construction clusters are local irregularity rather than domain breadth: the same conceptual dimensions use different punctuation or placement; compact and structured policy forms coexist; generic `profileProperty`, `uiStatement`, and `testStatement` sublanguages move discoverability into context; Sync and deployment/resource clauses encode several facts through fixed word order; and nearby concept families invite valid-concept/wrong-grammar errors.

Broad M17–M20 implementation would multiply parser, semantic, IR, completion, formatter, fixture, compatibility, and migration obligations around those shapes. M16.5 therefore requires an explicit keep/normalize/tooling/migrate decision first so later milestones do not accidentally fossilize avoidable surface irregularity.

## Work items

- [ ] **P1** Freeze a reproducible language-surface baseline from `tools/grammar_complexity_metrics.py` and the 16-family construction taxonomy before any normalization design is approved. **Depends on:** current normative grammar and grammar-complexity review. **Acceptance:** the baseline is reproducible in standard CI, records the current metric values and hotspot families, and contains no implementation/support claim or model score that was not measured.
- [ ] **P1** Produce one normalization decision matrix covering every measured high-risk family: colonized versus uncolonized leaves; `auth`, `errors`, `retry`, `timeout`, `consistency`, and `idempotency` variants; compact versus structured policy forms; `profileProperty`, `uiStatement`, and `testStatement`; compound word-order mini-languages; and confusable declaration families such as workflow/saga/task/schedule, event/topic/queue/channel, and value/view/entity/projection. **Depends on:** baseline. **Acceptance:** every row chooses and justifies one of keep-as-is, documentation/tooling clarification, schema-driven discoverability, deprecate/migrate, or candidate normalization; no row silently equates semantically different concepts merely because their syntax looks similar.
- [ ] **P1** Define a compatibility and migration contract for every candidate normalization that could change accepted source text. **Depends on:** normalization decision matrix and M7 compatibility authority. **Acceptance:** each breaking candidate identifies versioning boundary, old/new coexistence or deprecation policy, deterministic compatibility classification, migration/formatter or rewrite expectations where applicable, fixture strategy, rollback/rejection behavior, and the point at which old syntax ceases to be accepted; no breaking implementation may start without this contract.
- [ ] **P1** Define shared structural conventions for recurring policy dimensions without prematurely selecting concrete replacement syntax. **Depends on:** decision matrix. **Acceptance:** the plan explicitly separates transport error encoding from typed operation errors, error retry class from execution retry policy, API auth inheritance from operation authentication/authorization, and context-specific consistency/timeout semantics while identifying which structural conventions may safely converge.
- [ ] **P1** Decide whether compact and structured spellings remain intentional permanent forms. **Depends on:** decision matrix and compatibility plan. **Acceptance:** idempotency and other multi-field policy duals are inventoried; each retained dual has a documented construction/tooling rationale and canonical semantic equivalence rule where equivalence is intended; each removed dual has a migration path and compatibility treatment.
- [ ] **P1** Make generic sublanguages mechanically discoverable before expanding them. **Depends on:** M11 compiler-service direction and the decision matrix. **Acceptance:** `profileProperty`, `uiStatement`, and `testStatement` each have a planned compiler-owned source of legal keys/statements, value shapes, nesting, documentation, and completion data, with closed-schema validation ownership identified; parser permissiveness alone is not treated as editor/agent support.
- [ ] **P1** Decompose compound word-order mini-languages into named semantic facts for planning and compatibility review. **Depends on:** decision matrix. **Acceptance:** Offline Sync, deployment/resource, orchestration/retry, and similar compound leaves have an inventory mapping each ordered token/value segment to its semantic fact, downstream IR requirement, and potential migration sensitivity; later implementation may retain the surface unchanged if the evidence favors retention.
- [ ] **P2** Add explicit “choose this concept when…” construction guidance and future diagnostic/completion requirements for confusable declaration families before considering renames. **Depends on:** decision matrix. **Acceptance:** guidance covers workflow/saga/task/schedule, event/topic/queue/channel, and value/view/entity/projection; any rename remains a separate compatibility-sensitive language decision rather than a roadmap shortcut.
- [ ] **P1/P2** Run the M16 model- and vendor-neutral construction evaluation as a before/after comparison for any adopted normalization or tooling-only discoverability change. **Depends on:** M16 evaluation harness/task fixtures and a pinned repository baseline. **Acceptance:** identical task corpus and semantic end-state checks are used before and after; the report records model/runtime configuration as test metadata without making the roadmap vendor-specific; required metrics include compile success, semantic correctness, unnecessary edits, repair loops, regressions, first-pass parse rate, first-pass semantic-validation rate, invented-syntax rate, wrong-placement rate, diagnostics per 100 source lines, and semantic-fact recall; raw counts/deltas are published and no improvement is claimed unless measured.
- [ ] **P1** Gate broad M17–M20 surface expansion on a reviewed normalization decision. **Depends on:** all P1 items above. **Acceptance:** every hotspot has an explicit disposition, all breaking candidates have compatibility/migration requirements, baseline and before/after evaluation procedures are reproducible, and M17–M20 can reference stable construction conventions rather than independently choosing local syntax patterns.

## Acceptance criteria

- [ ] The deterministic grammar baseline and 16 construction families are reproducible and linked from the roadmap without inventing new measurements.
- [ ] Colon punctuation, recurring auth/errors/retry/timeout/consistency/idempotency forms, compact/structured duals, generic profile/UI/test sublanguages, compound mini-languages, and confusable concept families all have explicit evidence-backed dispositions.
- [ ] Every potentially breaking normalization is blocked on a versioned compatibility and migration contract owned by M7 semantics rather than by parser, generator, or migration tooling heuristics.
- [ ] Vendor-neutral M16 construction evaluation defines comparable before/after evidence using the same semantic task corpus and records results only when actually executed.
- [ ] No M16.5 completion item by itself changes syntax, parser acceptance, semantic meaning, Canonical IR, generator/runtime behavior, IDE support, profile status, or conformance claims.
- [ ] Broad M17–M20 implementation proceeds only after the gate establishes which existing forms are intentionally stable, which need discoverability/tooling, and which are approved candidates for a separately implemented migration.
