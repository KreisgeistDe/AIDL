# M10 Core consumer binding evidence

This focused closure narrows the remaining Core `consumer` Validate/IR gap without changing syntax, generator/runtime behavior, editor support, or the conformance matrix status.

The normative Core consumer boundary already requires `consumer NAME on EVENT from TOPIC`, Core delivery is at-least-once, and a bound consumer must consume an event declared by its source topic. `AIDL-DIST415` rejects a missing binding header, unresolved event/topic references, a bound event absent from the topic event contract, and a bound topic that omits explicit `atLeastOnce` delivery or declares a non-Core delivery mode. Diagnostics are deterministic, source-located, and emitted before Canonical IR construction.

`tools/test_core_consumer_binding_semantics.py` provides positive and negative executable evidence. The positive case proves that a valid binding remains diagnostic-free and that the already accepted Canonical IR deterministically preserves the resolved `eventId`, `topicId`, and existing consumer idempotency contract. Negative cases cover every rule added by this closure.

A follow-up execution-materialization slice now closes the part of the remaining consumer clauses whose meaning is both normatively established and already representable in the closed Canonical IR. For a full Core application build, the existing `AIDL-T005` materialization boundary now rejects an explicit `service` clause unless it resolves to a service that lists the consumer in `runs` and is included by the canonical system; this makes the source binding agree with the service relationship that Canonical IR can actually preserve. Fully specified `retry: exponential(initial: ..., maxDelay: ..., attempts: ...)` and `start: workflow|task ...` are accepted only when their required values/targets can be preserved without defaulting or unresolved references. `tools/test_core_consumer_execution_contract.py` proves deterministic preservation of the exponential retry budget, start target, and service `runs` relationship.

The same materialization boundary prevents full Core IR construction from silently widening or dropping grammatical forms that the closed IR cannot currently represent: `retry: immediate(...)`, `start: mutation ...`, consumer `call`, and consumer `transaction`. The transaction case remains especially deliberate: consumer grammar does not carry the isolation clause required by the normative Core transaction contract, so this slice does not invent an isolation default. These checks are scoped to the full canonical app/system materialization path; existing isolated M2 diagnostics for idempotency, transaction boundaries/isolation, and outbox semantics remain independent and unchanged.

`decl.consumer/validate` and `decl.consumer/ir` remain `partial`. The service/exponential-retry/workflow-or-task-start materialization slice is now covered, while immediate retry, call, mutation-start, and consumer-transaction semantics still require an authoritative contract plus matching IR representation before they can be accepted. M10 acceptance criteria 1 and 3 therefore remain open while criteria 2 and 4 remain complete.
