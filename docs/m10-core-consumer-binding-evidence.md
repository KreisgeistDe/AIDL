# M10 Core consumer binding evidence

This focused closure narrows the remaining Core `consumer` Validate/IR gap without changing syntax, generator/runtime behavior, editor support, or the conformance matrix status.

The normative Core consumer boundary already requires `consumer NAME on EVENT from TOPIC`, Core delivery is at-least-once, and a bound consumer must consume an event declared by its source topic. `AIDL-DIST415` rejects a missing binding header, unresolved event/topic references, a bound event absent from the topic event contract, and a bound topic that omits explicit `atLeastOnce` delivery or declares a non-Core delivery mode. Diagnostics are deterministic, source-located, and emitted before Canonical IR construction.

`tools/test_core_consumer_binding_semantics.py` provides positive and negative executable evidence. The positive case proves that a valid binding remains diagnostic-free and that the already accepted Canonical IR deterministically preserves the resolved `eventId`, `topicId`, and existing consumer idempotency contract. Negative cases cover every rule added by this closure.

A follow-up materialization slice now closes the consumer `service` contract that can be proved end to end without inventing execution semantics. In a full Core app/system build, the existing `AIDL-T005` materialization boundary requires an explicit consumer `service` reference to resolve uniquely, requires that service to list the consumer in `runs`, and requires the service itself to be included by the canonical system. `tools/test_core_consumer_execution_contract.py` proves that this accepted relationship is deterministic and preserved by the Canonical IR service `runs` list while retaining the existing consumer binding and idempotency facts.

The same full-IR boundary now rejects remaining consumer execution clauses that the current compiler would otherwise drop or widen. Non-`none` retry policies are not accepted yet: although exponential retry has normative source shape and an IR schema shape, executable evidence showed that the current consumer IR projection normalizes a valid exponential policy to `none`, while `immediate` has no closed IR representation. Consumer `start` is likewise kept outside the accepted boundary until target/effect projection is proven executable. Consumer `call` has syntax but no complete closed Core execution contract, and consumer `transaction on RESOURCE { ... }` omits the isolation required by the normative Core transaction contract. These forms therefore fail materialization instead of being silently reinterpreted. The checks are scoped to the full canonical app/system path so the existing isolated M2 idempotency, transaction-boundary/isolation, outbox, CLI, and explanation diagnostics remain unchanged.

`decl.consumer/validate` and `decl.consumer/ir` remain `partial`. The service-binding slice is now closed; non-`none` retry, start/call, and consumer-transaction semantics remain explicitly open pending matching normative and executable Canonical IR behavior. M10 acceptance criteria 1 and 3 therefore remain open while criteria 2 and 4 remain complete.
