# M10 Core consumer binding evidence

This focused closure narrows the remaining Core `consumer` Validate/IR gap without changing generator/runtime behavior, editor support, or the conformance matrix status.

The normative Core consumer boundary already requires `consumer NAME on EVENT from TOPIC`, Core delivery is at-least-once, and a bound consumer must consume an event declared by its source topic. `AIDL-DIST415` rejects a missing binding header, unresolved event/topic references, a bound event absent from the topic event contract, and a bound topic that omits explicit `atLeastOnce` delivery or declares a non-Core delivery mode. Diagnostics are deterministic, source-located, and emitted before Canonical IR construction.

`tools/test_core_consumer_binding_semantics.py` provides positive and negative executable evidence. The positive case proves that a valid binding remains diagnostic-free and that the already accepted Canonical IR deterministically preserves the resolved `eventId`, `topicId`, and existing consumer idempotency contract. Negative cases cover every rule added by this closure.

A follow-up materialization slice closes the consumer `service` contract that can be proved end to end without inventing execution semantics. In a full Core app/system build, the existing `AIDL-T005` materialization boundary requires an explicit consumer `service` reference to resolve uniquely, requires that service to list the consumer in `runs`, and requires the service itself to be included by the canonical system. `tools/test_core_consumer_execution_contract.py` proves that this accepted relationship is deterministic and preserved by the Canonical IR service `runs` list while retaining the existing consumer binding and idempotency facts.

The same executable evidence closes the normative consumer exponential-retry projection. Source `retry: exponential(initial: DURATION, maxDelay: DURATION, attempts: POSITIVE_INT)` is accepted only when all three parameters are present and positive; parser whitespace normalization is tolerated without changing the language syntax. Canonical IR deterministically preserves it as `retry.kind = exponential`, `attempts`, `initialDelayMs`, and `maxDelayMs`, matching the existing closed `spec/ir.schema.json` retry shape. Invalid exponential forms remain rejected by `AIDL-T005` rather than reaching IR with values that violate the schema.

The next proven slice closes Consumer `start` only where the normative grammar and closed Canonical IR overlap. Normative `consumerClause` permits `start: invocationKind expression` with `invocationKind = workflow | task | mutation`, while the existing IR `start` effect permits `targetKind = workflow | saga | task`. The implementation therefore accepts only `workflow` and `task` consumer starts. Their target must resolve uniquely through the same module/import resolution boundary used by the compiler, and Canonical IR preserves the exact target kind, resolved declaration ID, and input value. `tools/test_core_consumer_execution_contract.py` proves deterministic target-ID, target-kind, and record/symbol input projection for both accepted kinds.

The accepted Consumer `start` input is deliberately narrower than the full expression grammar. The current closed `valueExpr` projection can prove lossless preservation for literals, symbol paths, and recursively composed record literals; a Consumer `start` must supply exactly one invocation argument in that subset. More complex grammatical expressions remain rejected by `AIDL-T005` rather than being widened into an opaque symbol. This is a materialization boundary, not a language-syntax change.

Remaining consumer execution clauses are still bounded explicitly. `retry: immediate(...)` has no closed Core IR representation and remains rejected. `start: saga ...` remains rejected because the Canonical IR can represent that target kind but the normative Consumer grammar does not currently admit it. `start: mutation ...` remains rejected because the normative grammar admits it but the closed Core IR start effect does not. Consumer `call` has syntax but no complete closed Core execution contract, and consumer `transaction on RESOURCE { ... }` omits the isolation required by the normative Core transaction contract. These forms fail materialization instead of being silently reinterpreted. The checks are scoped to the full canonical app/system path so existing isolated M2 idempotency, transaction-boundary/isolation, outbox, CLI, and explanation diagnostics remain unchanged.

`decl.consumer/validate` and `decl.consumer/ir` remain `partial`. Service binding, exponential retry, and the proven workflow/task Consumer-start projection are closed slices; saga/mutation start, richer start-input expressions, immediate retry, call, and consumer-transaction semantics remain explicitly open pending matching normative and executable Canonical IR behavior. M10 acceptance criteria 1 and 3 therefore remain open while criteria 2 and 4 remain complete.
