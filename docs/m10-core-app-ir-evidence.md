# M10 Core app Canonical IR evidence

This focused closure records executable evidence for the already implemented Core `app` projection and the normative source-validation boundary for explicit profile selection, without widening syntax, generation, runtime, or editor support.

`tools/test_core_app_ir_semantics.py` proves that accepted Petstore app semantics are preserved deterministically in Canonical IR: stable app identity, `systemId`, `apiIds`, `defaultDeploymentId`, explicit profile `id`/`major` selections, and the existing global auth metadata (`provider`, `subjectClaim`, `roles`, `scopes`, and `serviceIdentities`). The same generated document is required to satisfy the closed Draft 2020-12 Canonical IR schema.

The same focused test now also exercises the normative accepted-source boundary with stable source-located `AIDL-DIST414` diagnostics. Core requires an `app` declaration with an explicit profile selection, `docs/06-grammar.md` fixes the permitted app-clause shapes, and `spec/profile-registry.json` fixes registered profile major versions and their `requires` dependencies. The compiler therefore rejects an app with no explicit profile clause, malformed profile or other app clauses that fall outside the normative grammar, unregistered profile/version pairs, and selected profiles whose registry dependencies are not explicitly selected.

Negative IR evidence continues to cover missing required `system`/`defaultDeployment` clauses, unresolved system/API/deployment references at IR construction, and malformed closed-schema app/profile/auth contracts including missing required app fields, unknown properties, malformed declaration IDs, invalid profile majors, and invalid service-identity values.

The source validator intentionally does **not** invent duplicate-clause or global-auth completeness rules. The normative app grammar is expressed as repeated `appClause` and does not state that repeated `profile`, `system`, `api`, or other app clauses are globally unique. Likewise, the normative `auth` grammar is a generic `profileProperty` block and the current profile registry names `auth.denyByDefault` but does not define a complete mandatory provider/subject/roles/scopes/service-identities clause set. Duplicate valid profile selections and a partial auth block therefore remain outside `AIDL-DIST414` until a normative source establishes a stricter rule.

`decl.app/validate` and `decl.app/ir` both remain `partial`. This closure removes the previously documented explicit-profile defaulting gap from the accepted validation path, but it does not exhaust every broader App validation/IR behavior: source-level uniqueness and auth-completeness rules remain intentionally unclaimed, while missing/unresolved system/API/deployment facts are still primarily bounded by Canonical IR construction and its closed schema rather than an exhaustive App source diagnostic contract.

M10 acceptance criteria 1 and 3 therefore remain open. Criteria 2 and 4 remain complete. No grammar, parser/resolver syntax expansion, generator, runtime, IDE, Ruleset, tag, release, or project `.ai/**` state is changed by this evidence block.
